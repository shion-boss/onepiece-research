## ⚠ このファイルに追記する時の規律 (人間 / routine 共通、 先に読むこと)

1. **「残り N 枚」 は必ず overlay の全走査で数える**。 そのバッチで目に入った分だけを
   残件数として書くと、 次に読む人が 「あと少し」 と誤認して打ち切る。
   実例 (2026-08-04): 任意コストの top-level `if` 問題を 「残 18 枚」 と記録したが、
   全走査すると **94 枚** あり、 しかも 「是正済」 と書いた範囲自体に 4 枚取りこぼしがあった。
2. **1 枚直したら 「それはパターンか」 を必ず問う**。 公式の構文・語の使い分け・overlay の型に
   起因するものは、 同型を機械で全部数えてからスコープを決める。
3. **一括変換は 「効果エントリ単位 × 対応するテキスト欄」 で行う**。 カード単位で JSON blob を
   置換すると別の節を巻き込む (OP11-061 の【トリガー】節を誤って書き換えた事故がある)。
   ⚠ 【トリガー】の文面は `text` ではなく **`trigger` フィールド** (820 枚)。
4. **同じ形の検査は 1 つに束ねて全語彙に当てる**。 コスト用の監査をパワーに広げた瞬間、
   コスト側の取りこぼしが 4 枚出てきた。
5. **違反でなかったものも記録する**。 記録しないと同じ調査を繰り返す。
6. **検査を足したら mutation で 「空でない」 ことを確かめる**。 緑でも中身が無い検査は無意味。
7. ⭐ **バックフィルテストは 「現在の overlay」 から書かれているので、 overlay が間違っていると
   バグを正解として固定する**。 裁定を是正したら **必ずフル pytest を回し、 落ちたテストが
   「旧バグを期待値にしていた」 ものかを確認して書き換える**。
   実例 (2026-08-04): 任意コストの是正で 3 件落ちた。 うち
   `test_op16_047_activate_main_absent_when_hand_lt8` は
   **「条件不成立なら起動メインが legal に出ない」 = 違反そのものを assert** していた。
   ⚠ `audit_test_circularity.py` はこれを検出できない (挙動テストではあるが、 期待値が
   overlay 由来で誤っている)。 **外部オラクル (公式 Q&A) と突き合わせるまで気づけない**。

## バトル中に当事者が場を離れたら **バトルは中断** される (2026-08-04 是正)

**一次情報** (`db/faq/cardqa_op_01 / op_05 / op_12 / st_02 / st_03` で繰り返し明示):

- 「カウンターステップの終了時に、 アタックしているキャラやアタックされているキャラが
  場に存在しない場合、 **ダメージステップには移行せず、 バトルは終了します**」
- 「バトルの途中 (アタックステップ/ブロックステップ/カウンターステップのいずれか) で、
  バトルをしているキャラが場を離れた場合、 **その時点でバトルは中断されます**」
- 「アタックした対象がいなくなった為、 その後のカウンターステップ、 ダメージステップは
  スキップされ、 バトルは終了します。 その場合、 このキャラの **"バトルした場合" は解決されず**」

**是正前の挙動**: engine は **アタッカーを object 参照で保持してバトルを続行** していた。
カウンターでアタッカーが KO されてもダメージが通っていた (実測: 相手ライフ 3 → 2)。
Rust もスナップショットで忠実にミラーしていたため **差分検証では原理的に検出できなかった**。

**実装**: `game.py:_battle_aborted()` をカウンターフェイズ直後 (= ダメージステップの直前) に
3 経路すべてで呼ぶ。 Rust も同じ位置でガード。
⚠ Rust では `find_tagged` が **タグを消費する** ので、 それ以降は `atk_tok` で引けない。
アタッカーの生存確認は消費されない `state.current_attacker_tok` を使うこと。

**恒久ガード**: `tests/test_effect_interactions.py`
`test_battle_aborts_when_counter_kos_the_attacker` (+ 中断されない対照ケース)。

**一次情報** (3 つの弾で同じ裁定が繰り返されている = 一般則):

> 「レストにできない」と書かれた効果は、そのキャラが…

> - **【ブロッカー】を発動**することができなくなる効果ですか？ → 「はい、発動できません」
> - 他のカードの効果で**レストにする**ことができなくなる効果ですか？ → 「はい、レストにできません」
> - 「このキャラをレストにする」などと書かれた**効果を発動**することができなくなる効果ですか？
>   → 「はい、発動できません」
>
> いずれも理由は共通: **「アタックや【ブロッカー】の発動などの、レストにすることが必要な行動を
> できない状態にする効果です」**

**engine の状態 (2026-08-04 調査時)**:

| 行動 | 是正前 | 対応 |
|---|---|---|
| アタック | ✅ 正しく止まっていた | — |
| 他効果によるレスト | ✅ 正しく止まっていた | — |
| **【ブロッカー】発動** | ❌ `rested` しか見ておらず素通り | ブロッカー適格判定に追加 (Python `game.py` 2 / Rust `rules.rs` 2) |

実装されていた = **「一部だけ実装」 は最も見つけにくい形**。 裁定が列挙している行動は全部当たること。

## 公式どおりで **問題なかった** もの (再調査を避けるための記録)

- **【バニッシュ】の適用範囲** — 「【バニッシュ】は、**アタックによるダメージで**ライフから
  手札に加えるカードを、代わりにトラッシュに置く効果」。 engine は `is_banish_now` を
  アタック解決経路でしか読んでおらず、 効果によるライフ→手札には適用していない = 正しい。
- **【ダブルアタック】の判定時点** — 「ダメージステップより前に (条件) を失った場合、
  このキャラは【ダブルアタック】を失い、 リーダーへ与えるダメージは 1」。 engine は
  `is_double_attack_now` を **カウンターフェイズより後** に読んでいる = 正しい。
- **「A。 その後、 B」 の後段は前段が空振りでも実行される** — 「-4000しなかった場合も、
  **可能な限り**ライフ1枚を手札に加えます」。 engine は do 配列を最後まで回す = 正しい。
  (⚠ ただし **順序** は 19 件が逆だった。 上記の是正項目を参照)
- **ライフ 0 の扱い** — 「ライフの上から1枚を手札に加える」 は **できない**、
  「デッキの上から1枚をライフの上に加える」 は **できる**。 どちらも正しい。
- **【トリガー】の発動は 「イベントの発動」 ではない** — 「【トリガー】の発動はイベントの発動と
  異なります」。 engine の `trigger_lifecard_trigger` は `opp_event_or_trigger_fired` と
  `on_self_trigger_fired` は発火するが **`on_self_event_played` は発火しない** = 正しい。
  (手札から効果でイベントを発動する `play_event_from_hand` は 「発動」 なので発火する = これも正しい)
- **【アタック時】で KO されたキャラの【相手のアタック時】は発動しない** — engine は
  `fire_on_attack` の **後** に場を走査して opp_attack を積むので、 KO 済のキャラは
  そもそも走査対象に居ない = 構造的に正しい。
- **【カウンター】でアクティブにしたキャラは そのバトル中ブロックできない** —
  「既にこのバトルのブロックステップは終了しているため」。 engine は `blocker_iid` を
  **action の一部** (= アタック宣言時に確定) として持ち、 カウンターステップはその後に
  解決されるので、 そこから新たにブロッカーになる経路が構造的に存在しない = 正しい。

## 「(場のキャラをライフに)置く：相手は手札を捨てる」 の後段は **置いた場合のみ** (2026-08-04 是正)

**一次情報** (`db/faq/cardqa_*` OP09-101 クザン):

> 「このキャラを登場させ、相手のコスト3以下のキャラ1枚を相手のライフに置かない事はできますか？」
> → **「はい、できます。その場合、相手は手札1枚を捨てることはありません。」**

対象カード = **OP09-101 クザン** 「【登場時】相手のコスト3以下のキャラ1枚を、相手のライフの
上か下に表向きで置く：相手は自身の手札1枚を捨てる。」

**是正前の挙動**: overlay の do が `[{"trash_opp_hand_random": 1}, {"chara_to_opp_life": ...}]`
の **2 段独立** で、 (a) 順序が公式と逆 (捨てが先) (b) **ライフに置けない/置かない場合でも
相手に手札を捨てさせていた**。 実測: 相手にコスト3以下のキャラが 1 体も居ない状態で登場させると
相手の手札が 4→3 に減った = 公式違反。 Python/Rust とも同じ overlay を読むので
**差分検証では原理的に沈黙** していた。

**実装**: `chara_to_opp_life` プリミティブに optional `then` サブ効果を追加し、
**実際に 1 枚以上置いた時のみ** (`placed > 0`) 発火するようにした (Python `effects.py` /
Rust `effects.rs` 両方)。 overlay を
`{"chara_to_opp_life": {"target": "one_opponent_character_cost_le_3", "then": [{"trash_opp_hand_random": 1}]}}`
に組み替え (置く=前段、 捨てる=後段=置いた時のみ)。
⚠ `if` 条件でゲートする案は不可: target 解決は印刷コスト (`card.cost`)、
`exists_opp_chara_cost_le` 条件は `base_cost` と **基準が異なり** ズレる。 実際に置けたか
(placed) でゲートするのが唯一正確。 RNG 順序は不変 (置く処理は RNG を消費しないので、
後段の random discard が引く手札は同一)。

**恒久ガード**: `tests/test_effect_interactions.py`
`test_op09_101_no_discard_when_no_life_target` (対象なし→捨てなし) +
`test_op09_101_discards_when_life_target_placed` (対照: 置いた場合は捨てる)。

## 公式どおりで **問題なかった** もの (2026-08-04 追加分、 FAQ 全件保証 台帳より)

- **リダイレクト系【相手のアタック時】は攻撃側のキーワードに依存しない** (OP14-060 ドフラミンゴ) —
  「【速攻】を持つキャラが登場ターンにアタックした場合でも、 対象をリーダーに変更できますか？」
  →「はい」。 engine の `redirect_attack` は候補 (`self_leader` / 特徴フィルタ) をアタッカーの
  キーワードと無関係に決めるので、 速攻でも同じく発動 = 構造的に正しい。
- **`set_base_power_timed` は代入 (加算でない)** (ST26-005 ルフィ) — 「【登場時】/【アタック時】を
  2 回発動したターン、 リーダーの元々のパワーはいくつ？」→「7000」。 override フィールドへの代入
  なので 2 回発動でも 7000 (14000 にならない)。 実測 `base_power` 5000→7000→7000。
- **`in_hand_cost_minus` は該当 in_hand effect 毎の加算 (一致キャラ数で乗算しない)** (ST26-001
  おそばマスク) — 「7000+ の『サン五郎』と『サンジ』が両方いる場合コスト-10 か？」→「いいえ、 -5」。
  `game.py:_in_hand_cost_minus` は条件を満たす in_hand effect の `in_hand_cost_minus` を合計する
  だけで、 フィルタ一致キャラ数は掛けない = flat -5 = 正しい。
- **条件 `self_chara_filtered_count_ge` は発動元 (自身) を数える** (ST14-007 ロビン) —
  「このキャラ自身のコストが8以上なら『自分のコスト8以上のキャラがいる』を満たすか？」→「はい」。
  発動元は `me.characters` に含まれるので自身も数える = 正しい (self-inclusion 実測確認)。
  ⚠ ただし `cost_ge` は印刷コスト判定 = 「コストN以下/以上」の印刷コスト問題 (587 枚 escalated 済)

## 素の 「コストN」 は **OR (or_clauses) の中でも現在コスト** (2026-08-04 是正)

**一次情報** (`db/faq/cardqa_`、 P-084 バギー):

## 「相手がイベント/【トリガー】を発動した時」 の reactive は、 反応対象の効果を **処理した後** に解決する (2026-08-04 是正)

**一次情報** (`db/faq/cardqa_op_06`、 OP06-044 ギオン):

> 「相手がイベントの【カウンター】効果を発動した時、 この【自分のターン中】効果で相手は自身の
>   手札1枚をデッキの下に置くのは、 その【カウンター】効果の処理を行う前ですか？」
> → **「いいえ、 相手が使用したイベントの【カウンター】効果を処理した後、 この【自分のターン中】
>     効果で相手が自身の手札1枚をデッキの下に置きます。」**

OP06-044 ギオン【自分のターン中】【ターン1回】= 「相手がイベントを発動した時、 相手は自身の手札
1枚をデッキの下に置く」 (overlay `opp_event_or_trigger_fired`)。 反応の発火は 「イベント発動そのもの」
への割り込みではなく、 **反応対象のイベント (カウンター) の効果が完全に解決した後**。

**是正前の挙動 (Python のみ)**: `_pop_next_event` は `owner_idx == turn_player_idx` のイベントを
優先して pop する (= 同時トリガーの公式ルール 7-x)。 だが 防御側が撃った カウンターイベント
(owner=防御側=**非** turn) と、 それに反応する ギオンの reactive (owner=攻撃側=**turn**) を同時に
キューへ積むと、 turn 優先で **reactive が先に pop** され、 「ギオン→カウンター効果」 の逆順に
なっていた。 実測: 是正前 = 「ギオンで手札→デッキ下」 → 「カウンター -3000」、 是正後 =
「カウンター -3000」 → 「ギオンで手札→デッキ下」。

**Rust は元々正しかった**: `fire_counter_events` / `execute_main_event` /
`trigger_lifecard_trigger` は `execute_card_effects("counter"/"main"/…)` を **inline で先に実行** し、
その後 `fire_field_when(…, "opp_event_or_trigger_fired")` を呼ぶ構造 (= event 先→reactive 後)。
Rust 作者はコメントで 「Python の順 = counter→opp_event」 と **意図** を書いていたが、 Python の
実行時挙動 (turn 優先) はそれと食い違っていた。 = **Python が Rust の忠実ミラーから外れていた**
稀な向き。 両効果が独立ゾーン (手札 vs パワー) を触る限り最終 digest は同一なので rust_parity は
沈黙していた (= 順序差が状態差に化けるのは両効果が同一資源を奪い合う時のみ)。

**実装 (Python のみ、 Rust は無変更で既に正)**: `trigger_counter_event` /
`trigger_main_event` / `trigger_lifecard_trigger` で、 triggering event を enqueue した直後に
`_maybe_resolve(state)` を挟んで **先に drain** してから `trigger_opp_event_or_trigger_fired`
(+ `trigger_self_event_played` / `on_self_trigger_fired`) を積む。 main event は元々
event=turn 側で FIFO により event 先だったので実質不変。 counter / life-trigger (event=非turn 側)
が実際の是正対象。 影響 reactive = `opp_event_or_trigger_fired` 保有 6 base card

## 条件付き【速攻】は 「相手の場のドン枚数」 を毎回再評価する (2026-08-04 是正、 EB02-061)

**一次情報** (`cardqa_eb_02`、 EB02-061 モンキー・D・ルフィ):

> 「自分のターン中、 相手のドン!!が5枚あるときにこのキャラを登場し、 その後他の効果で
>   相手のドン!!が4枚になりました。 この場合、 このキャラはアタックできますか？」
> → **「いいえ、 できません。」**

EB02-061 のカードテキスト = 「自分のリーダーが多色で、 **相手の場のドン!!が5枚以上ある場合**、
このキャラは【速攻】を得る。」 = **2 条件の AND** (多色リーダー ∧ 相手ドン≥5)。 相手ドンが4枚に
減った瞬間【速攻】を失い、 召喚酔いのキャラはアタックできなくなる。

**是正前の挙動**: overlay の `on_attached_don n=0` の `if` が **`leader_color_multi` だけ** で
`opp_don_count_ge:5` が **欠落** していた。 その結果、 多色リーダーでありさえすれば相手のドン枚数に
関わらず【速攻】が付与され、 相手ドン4枚でも登場ターンにアタックできてしまっていた (公式違反)。
Python/Rust とも同じ overlay を読むので **差分検証では原理的に沈黙** するクラス。

**実装**: overlay のみ是正。 EB02-061 の **全 5 variant** (EB02-061 / _p1 / _p2 / _p3 / _r1) の
`if` に `opp_don_count_ge:5` を追加。 `opp_don_count_ge` は Python (effects.py:1919、 相手の
active+rested+付与ドン合算) / Rust (effects.rs:760、 `total_don(opp)`) 両方が bit 一致実装済 →
engine コード無変更で両エンジン是正。 実測: 相手ドン5枚→【速攻】付与 / 相手ドン4枚→付与なし。

**恒久ガード**: `tests/test_effect_interactions.py::test_eb02_061_conditional_rush_requires_opp_don_ge_5`
(相手ドン5→速攻あり / 相手ドン4→速攻なし の対照)。 mutation 確認済 (opp_don_count_ge を外すと
「相手ドン4枚でも速攻」 で落ちる)。

⭐ **教訓**: カードテキストが 「A で、 B の場合」 と **2 条件の AND** を書いている効果は、 overlay の
`if` に **両方** 入っているかを確認する。 片方だけだと 「条件不足で常時発動」 = 最も見つけにくい形。

## 「〜できる：<条件>の場合、<効果>」 は **リーダー条件でも** コストを払える (2026-08-05 決着)

前の項 (任意コスト gate) を **リーダー特徴/名の条件にも適用してよいか** が escalated のまま
残っていた (「直接 Q&A が無い」 という理由)。 **一次情報は存在した**:

| 一次情報 | 答 |
|---|---|
| `cardqa_op_02` 「自分のリーダーが特徴《インペルダウン》を持たない場合、この【メイン】効果の**発動コストで手札を捨てることはできますか？**」 | **「はい、できます。その場合、カード2枚を引くことはできません。」** |
| `cardqa_op_02` 「自分のリーダーが「エンポリオ・イワンコフ」ではない場合、この【起動メイン】効果を発動できますか？」 | **「はい、できます。その場合、このカードをレストにしますが、その後の効果では何も起きません。」** |
| `cardqa_st_04` 「自分のリーダーが《百獣海賊団》を持たない場合、この【起動メイン】効果を発動できますか？」 | **「はい。発動できますが、何も起きません。」** |
| `cardqa_op_01` 「自分のリーダーが「光月おでん」ではない場合、このキャラを登場させることはできますか？」 | **「はい。【登場時】効果のコストは支払うことも支払わないこともできますが、効果は何も起きません。」** |

**対照 (= 効果側は止まる)**: 「リーダーが《ドンキホーテ海賊団》を持たない場合、この【登場時】効果で
自分のドン!!1枚までをアクティブにできますか？」 → 「**いいえ、できません**」。
= **コストは払える / 効果は起きない** で一貫している。

**コストの定義** (`cardqa_st_06`): 「**「：」以前に表記されている指示はすべて "発動コスト"** であり、
"発動コスト" はその一部のみを支払うことはできません。 また "発動コスト" の一部あるいは全部が
支払えない場合、 その効果を発動することができません。」
→ **コロンより前がコスト、 後ろは効果**。 効果側の条件がコストを妨げないのは この定義の帰結。

**是正**: 上記の読みで overlay を一括変換した (**123 エントリ / 70 base カード**)。
top-level `if` → `conditional` で効果側のみを包む。 `cost` ブロックはそのまま。

⚠ **AI の無駄払いを先に潰してから変換した**。 変換すると 「条件不成立でも任意コストを払える」
= AI がコストだけ払って何も起きない手を選べるようになる。 実測で **GreedyAI / GoalDirectedAI が
3/3 で無駄払い** した (配備の ExploitBeam は beam eval で 0/3 = 元から正しい)。
未知デッキは greedy に degrade するので実害があり、 先に
`GreedyAI._is_activate_effect_all_gated_off` で 「do が全部 conditional かつ全条件 false」 の
起動メインを **選ばない** ようにした (legal からは消さない = 人間は払える)。

⚠ **旧挙動を固定していたテストが 20 件落ちた** (「リーダー条件不成立なら起動メインが legal に
出ない」 等)。 バックフィルは現在の overlay からテストを書くので、 この形の退行固定は必ず起きる。

**恒久ガード**: `tests/test_effect_interactions.py`
`test_no_optional_cost_remains_gated_by_post_colon_condition` (全カード・全語彙を機械走査) +
`test_optional_cost_missing_backlog_is_tracked` (下記の残債務を固定)。

### ⚠ 残債務: 任意コスト自体が overlay に未実装 = **タダ撃ち** (26 枚)

「〜できる：」 のコストが overlay に無く、 効果だけが無料で起きるカードが **26 枚** ある

## ⚠ 「〜できる：」 の判定は **カード全体でなく その効果の節** で行う (2026-08-05)

前項の一括変換で **2 種類の誤検出** を出したので、 判定手順を確定させる。

### 誤り① カード全体の `text` で判定すると 別の節の 「できる：」 を拾う

1 枚のカードは複数の節を持ち、 節ごとに 「〜できる：」 の有無が違う。 実例:

> **EB03-006 ナミ**: 「【登場時】自分のアクティブのリーダーを…パワー-5000**することができる：**
> カード1枚を引く。【起動メイン】【ターン1回】自分のリーダーが特徴《アラバスタ王国》を持つ場合、
> 相手のキャラ1枚までを…パワー-1000。」

【起動メイン】節には 「できる：」 が **無く**、 リーダー条件は **発動条件そのもの**。 だが
カード全体の text を見ると【登場時】節の 「できる：」 が引っかかり、 発動条件を効果側へ移して
しまった (= 条件不成立でも起動できる誤り)。 **`when` に対応する節だけを切り出して判定する**。
⚠ 【起動メイン】【ターン1回】 のように修飾マーカーが連続するので、 節の切り出しでは
【ターン1回】【ドン‼×N】 を読み飛ばす必要がある。

逆に この誤りは **取りこぼし** も生む: 節単位に直したら EB02-041 / EB02-052 / OP14-020 の
3 枚が新たに該当した (カード全体だと 「コロン前にも 『場合』 がある」 と誤判定して除外していた)。

### 誤り② コストは `cost` ブロック **以外** にも書かれている

`optional_cost_then` は **primitive の中に cost を持つ** 形。 `eff.get("cost")` だけを見て
「コスト未実装 = タダ撃ち」 と判定すると **19 枚を誤検出** する。 実際に一度
「26 枚がタダ撃ち」 と数えて 23 枚に `cost` ブロックを足しかけたが、 それらは
`optional_cost_then` 内に既にコストを持っており、 **二重コストになるところだった** (commit 前に破棄)。

**正しい判定**: `eff.get("cost")` が無く、 かつ `optional_cost_then` も無い時だけ 「未実装」。
この基準で数え直すと **真のタダ撃ちは OP15-109 ニコ・ロビン 1 枚だけ** だった
(「自分のライフの上から1枚を手札に加えることができる：」 → `life_to_hand: 1` を実装)。

**恒久ガード**: `tests/test_effect_interactions.py`
- `test_converted_cost_not_gated_entries_really_have_optional_cost` — `[cost-not-gated]` を
  付けた効果が **自分の節に** 「できる：<条件>」 を持つことを全数確認 (誤り① を止める)
- `test_optional_cost_missing_backlog_is_tracked` — `optional_cost_then` も数えたうえで
  タダ撃ち **0 枚** を固定 (誤り② を止める)

⭐ **教訓**: 「公式テキストと overlay を突合する検査」 は、 **テキストの切り出し単位** と
**overlay 側の表現ゆれ** の両方を先に確定させてから数える。 どちらを外しても
「多すぎる誤検出」 と 「見えない取りこぼし」 が同時に起きる。

>   持つキャラが相手の効果で場を離れる代わりに自分のドン‼1枚をレストにできますか？」

P-111【ターン1回】= 「自分の特徴《麦わらの一味》を持つキャラが相手の効果で場を離れる場合、
代わりに自分のドン‼1枚をレストにできる。」 レストにできるのは **アクティブのドン** なので、
アクティブが無ければ この置換 (= 場離れの肩代わり) は成立せず、 キャラは通常どおり場を離れる。

**是正前の挙動**: overlay が `rest_self_don` を **`do` 側** に持ち、 `cost` は `[{once_per_turn}]`
だけだった。 `_can_pay_replace_cost` は once_per_turn しか見ないので **常に払える扱い**、

最初から cost 側で正しかった)。

`rust_engine/src/effects.rs`) に `rest_self_don` の payability (`don_active >= N`) と支払い
(アクティブ N 枚→レスト) を追加。 影響カード = **P-111** (1枚) / **OP10-074 ピーカ**

## 「(条件)の場合、…。その後、公開カードをデッキの下に置く」 の後段は 条件節の中 (2026-08-05 是正、 EB01-029)

**一次情報** (`db/faq/cardqa_eb_01`、 EB01-029 わりいおれ死んだ):

> 「この【カウンター】効果で公開したカードのコストが3以下だった場合、公開したカードはどうなりますか？」

## OP01-011 ゴードン 【登場時】: 任意コスト (手札→デッキ下) が gate されず タダ撃ち = escalated (2026-08-05)

**一次情報** (`cardqa_op_01`、 OP01-011 ゴードン):

> 「自分の手札が他にない場合、このキャラを登場できますか？」
> → **「はい、登場できます。その場合、【登場時】効果は発動できません。」**

OP01-011【登場時】= 「自分の手札1枚をデッキの下に置く**ことができる**：カード1枚を引く」。
= 「〜できる：効果」 の任意コスト型。 コスト (手札1枚→デッキ下) を払えない (= 手札にこのゴードン
以外のカードが無い) 場合、 効果 (1ドロー) は **発動できない**。

**確認したバグ** (Python/Rust **同一 overlay** = 差分検証では沈黙):
overlay が **flat** `"do": [{"self_hand_to_deck_bottom": 1}, {"draw": 1}]` で、 cost gating が無い。
→ 手札 0 で登場させると `self_hand_to_deck_bottom` は no-op、 続く `draw` が **無条件発火** =
タダ撃ち (実測: `hand 0→1 / deck -1`)。 公式は 「効果は発動できません」。

**なぜ escalated か** (task rule 11 + 近似禁止):
- **faithful fix は `optional_cost_then` で包む** こと (他 63 枚のデッキ下コストはこの型)。 だが
  `optional_cost_then` の cost handler 群 (`effects.py` payability ~8767 / payment ~9040、
  Rust `effects.rs` ~2872/3175) には **`stage_to_deck_bottom` / `return_self_chara_to_deck_bottom`
  はあるが 「手札→デッキ下」 の cost が無い**。 → **Python + Rust 両方に cost handler を新設**
  (payability = `len(me.hand) >= N` / payment = 既存 `self_hand_to_deck_bottom` effect を再利用、
  discard_hand と同じ human-pick pause/continuation 対応) する **dual-engine 変更 + Rust rebuild +
  parity 再検証** が要る。
- **overlay-only の代替 `conditional{if:{self_hand_ge:1}, then:[put, draw]}` は不可**: 「できる」 の
  **任意性 (プレイヤーが払わない選択)** を潰す = 近似禁止 (公式テキスト忠実主義) に抵触。
- 1 バッチ (10 件) の full 検証を既に消化済のため、 engine cost primitive 追加は **次の集中回** で
  full attention 下に入れるのが安全 (cron 枠で急ぐと parity を壊す)。

**同型 (scoping 全走査、 「デッキ下に置くことができる：」 cost = 65 エントリ中 63 が
`optional_cost_then` で正)**: 未 gate は **3 base のみ**:
- **OP01-011 ゴードン** (手札→デッキ下 cost、 上記 = 手札版 cost handler 要 = escalated)
